## Незмінні правила (privacy-контракт; порушення = зупинка і перепланування)

1. Web залишається повністю робочим local-only на кожному коміті. Фаза 1 не
   додає жодного UI-affordance синхронізації чи нагадувань.
2. Медичні значення ніколи не потрапляють в URL, логи, аналітику, тексти помилок
   чи Telegram. Логи — лише білим списком §11.
3. **Назва згоди (`kind`) не потрапляє в URL, в `error_code` і в `outbox.payload`.**
   Набір активних згод — це health-inference. Тому `POST /v1/consents/revoke`
   із `kind` у тілі, а не `DELETE /v1/consents/{kind}`.
4. **У логах — `account_ref`, а не `account_id`.** `account_ref` = перші 16 hex
   від `HMAC(k_log, account_id)`, ключ з епохою 7 днів. Сирий `account_id` у лог
   не пишеться взагалі. IP-адреса не пишеться на диск ніде.
5. Сервер не аналізує вміст записів. У Фазі 1 медичних ендпоінтів немає взагалі —
   це DoD-пункт, а не побажання.
6. `BOT_TOKEN` ніколи не потрапляє в env/конфіг api-процесу (лише bot і
   `reminder_worker`; api отримує `TELEGRAM_BOT_ID` + публічний Ed25519-ключ).
7. Тексти згод не вигадуються і не редагуються «щоб краще звучало» — вони
   ухвалені й лежать у progress-файлі.

## Обсяг Фази 1

**Робиш:**

- Ed25519-валідація initData (§8) з офіційними тест-векторами; негативні кейси:
  зіпсований підпис, прострочений `auth_date`, відсутній `signature`.
- Anti-replay через `auth_replay` + конфіг-прапорець `min_auth_date`.
- Атомарний `POST /v1/auth/telegram` — три гілки §8 (є identity → сесія;
  немає акаунта і немає `grant` → 403 `no_account` і **нуль рядків**; немає
  акаунта + є `grant` → одна транзакція).
- Opaque-сесії (256-bit, у БД лише SHA-256), TTL 7 днів, sliding ≤30 днів,
  `GET /v1/sessions`, `POST /v1/sessions/revoke-others`.
- Step-up рівно за таблицею §8 — не ширше і не вужче.
- Ендпоінти згод: `GET /v1/consents`, `POST /v1/consents`,
  `POST /v1/consents/revoke`.
- Реєстр текстів згод + `text_version` + `text_sha256` + CI-звірка.
- Erasure акаунтів без активних згод за правилом `revoke_reason`.
- Міграція `0002` (дельта §6.2).
- Лог-процесор з allowlist і `account_ref`.

**Не робиш (це Фази 2–4):**

- жодного ендпоінта `/v1/sync/*`, жодної крипто-логіки, жодного `vault_*`-коду
  поза DDL міграції;
- жодного воркера нагадувань, жодного виклику Bot API;
- жодних змін у `apps/bot`;
- жодного UI у `apps/web`.

## Рішення Gate D, які Фаза 1 зобов'язана втілити

### Дві дельти з нагадувань (рішення заморожене зараз, реалізація — Фаза 4)

1. Колонка `consent.revoke_reason text NULL CHECK (revoke_reason IN
   ('user','bot_blocked_timeout','stale_text_timeout'))`. Назва саме
   `revoke_reason` (узгоджується з `revoked_at`).
2. Grant-контракт: `POST /v1/consents {kind, text_version, text_sha256, settings?}`,
   де `settings` обов'язковий **тоді і тільки тоді**, коли
   `kind == 'telegram_reminders'`, і дорівнює `{time, timezone}`. Схеми strict
   із `extra="forbid"`, тому це має бути один контракт, а не два.

### Чотири гачки з retention

1. `min_auth_date` — конфіг-прапорець валідатора initData (після restore
   `auth_replay` відкочується, і старі initData знову стають «новими»).
2. `deletion_copy_version text NOT NULL` у `erasure_job` — редакція обіцянки
   §6.4, чинна на момент запиту.
3. Запис у erasure-журнал виконується **перед** початком стирання. Якщо запис не
   вдався — erasure не стартує. У Фазі 1 це потрібно вже для sweeper акаунтів
   без згод.
4. Строк стирання акаунта без активних згод залежить від `revoke_reason`:
   `user` → негайно в тій самій транзакції (SLO p95 ≤ 60 с, стеля 15 хв);
   `bot_blocked_timeout` / `stale_text_timeout` → 30 діб. Попередній єдиний
   TTL 24 год **скасовано**.

### Один рядок із криптомоделі

Таблиця step-up у §8: відкликання будь-якої згоди — **без** step-up (Art. 7(3));
повне видалення акаунта, `vault-reset`, `re-key` і будь-який запис у
`/v1/sync/key` — **зі** step-up. У Фазі 1 реалізується лише перша половина, але
константа/enum операцій має бути заведена повністю, щоб пізніше ніхто не
«підсилив» і не «послабив» її з добрих намірів.

### Модель згод

- Рівно три `kind`; перейменування в нейтральні ідентифікатори відхилено.
- `cycle_sync` вимагає активної `health_sync` (інакше 409 `consent_precondition`)
  і каскадно відкликається разом із нею в тій самій транзакції.
- `text_version` у форматі `<kind>@<major>.<minor>`.
- Grace period / undo на відкликання **не вводиться**.
- Відкликані рядки `consent` живуть не довше 24 місяців після `revoked_at`.

## Блокер, який ти не маєш права обійти

Тексти згод перебувають у версії **`0.9`** і містять плейсхолдер
`[ім'я контролера]` у трьох місцях. Заморозити їх на `1.0` можна лише разом із
реальним іменем і контактом контролера, якого власник ще не назвав.

**Тобі заборонено:** вигадувати ім'я, підставляти будь-що замість плейсхолдера,
позначати copy як `1.0`, або писати код, який мовчки приймає згоду з
незамороженим текстом у production-конфігурації.

**Тобі дозволено і потрібно:** реалізувати весь механізм на текстах `0.9` як на
фікстурах, включно з CI-звіркою хешу; додати fail-closed guard, який відмовляє
у створенні згоди, якщо активна версія тексту має major `0` **і** конфіг не в
режимі розробки. Guard має бути під тестом.

Це не формальність: `text_sha256` хешує показаний текст, а ім'я контролера —
матеріальне поле, зміна якого потребує повторної згоди від усіх користувачок.

## Дисципліна якості

- **TDD**: спершу тест, який падає, потім реалізація. Для транзакційних сценаріїв
  (атомарний auth+grant, каскадне відкликання, гонка «нуль згод → erasure») —
  інтеграційні тести на реальній PostgreSQL через testcontainers.
- **Локальний Docker.** На цій машині testcontainers падає з
  `mkdir /host_mnt/.../docker.sock: operation not supported` — Ryuk не може
  змонтувати сокет Docker Desktop. Робочий обхід:
  `TESTCONTAINERS_RYUK_DISABLED=true uv run --locked pytest`. Це локальна
  особливість середовища, а не дефект тестів; у CI прапорець не потрібен.
- **Міграція `0002`, а не правка `0001`.** `0001` уже застосована й змерджена;
  переписування зруйнувало б downgrade→upgrade-тест Фази 0. Нова міграція мусить
  мати робочий `downgrade`.
- **Наскрізні gates перед закриттям фази** (усі мають бути зеленими):

```bash
pnpm test && pnpm build && pnpm e2e
```

```bash
cd apps/api && TESTCONTAINERS_RYUK_DISABLED=true uv run --locked pytest && uv run --locked ruff check . && uv run --locked ruff format --check . && uv run --locked mypy --strict app && uv run --locked lint-imports
```

```bash
cd apps/bot && uv run --locked pytest && uv run --locked ruff check . && uv run --locked mypy --strict bot
```

- Роутери тонкі; вся бізнес-логіка в `app/services/*`; ORM і сесії не вище
  `infra/db/repositories`; жодного SQL у роутерах. Контракти import-linter —
  механічна перевірка цього: **не переписуй контракт під код, переписуй код під
  контракт.**
- `main` під strict branch protection: працюй у гілці й відкривай PR. Комміти з
  префіксом `phase-1:`. Секрети не комітити ніколи.

## DoD Фази 1 (acceptance-критерії)

Фаза не завершена, поки кожен пункт не закритий тестом або артефактом. Повний
перелік — у `docs/plans/backend-bot-plan-progress.md`, розділ «Фаза 1», разом із
блоком «Додано рішеннями Gate D». Наприкінці фази онови цей файл: заміни
`_pending_` на конкретний доказ (назва тесту, номер CI-прогону).

Мінімум, що має бути під тестом:

- валідатор initData — 100% branch coverage; прострочений `auth_date` →
  `auth_stale`; повторний initData → 401;
- скасування діалогу згоди → **нуль рядків у БД**;
- конфіг api не містить `BOT_TOKEN` (незалежно від стану feature-флага);
- `text_sha256` показаного тексту == збережений;
- `cycle_sync` без `health_sync` → 409 `consent_precondition`;
- `telegram_reminders` без `settings` → 422 і нуль рядків;
- OpenAPI: жоден path-шаблон не містить назви згоди;
- відкликання без step-up; повне видалення — зі step-up;
- лог-капчур: нуль initData, нуль сирого `account_id`;
- медичних ендпоінтів немає.
