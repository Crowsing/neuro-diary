## Незмінні правила (privacy-контракт; порушення = зупинка і перепланування)

1. **Сервер ніколи не бачить plaintext медичних даних.** Це криптографічний
   факт, а не політика: шифрує і розшифровує виключно клієнт.
2. **Plaintext-заголовка шляху немає.** `record_key` непрозорий; сервер не знає
   навіть дат записів. Мапування `record_key → шлях` клієнт відновлює офлайн
   через HMAC-таблицю (§7). Це прибрано з плану свідомо — не повертай.
3. **Публічний API крипто-модуля — `encrypt(plaintext, aad)`.** Параметра
   `nonce` немає і не з'явиться. Nonce генерується всередині виклику
   `crypto.getRandomValues` і ніколи не виводиться з `record_key`, revision,
   лічильника або часу.
4. **При ретраї чанка клієнт надсилає байт-у-байт ідентичний payload** і
   ніколи не перешифровує його наново.
5. Медичні значення й назви згод — ніколи в URL, логах, аналітиці, текстах
   помилок, Telegram. Логи — лише за allowlist §11.
6. `BOT_TOKEN` не потрапляє в api. Браузерний Sentry заборонений назавжди
   (§6.5), error tracking у v1 не розгортається.
7. initData читається один раз, тримається в пам'яті модуля, одразу після
   читання — `history.replaceState` для зачистки `#tgWebAppData` і видалення
   `__telegram__initParams` із sessionStorage.
8. Local-only режим лишається повністю робочим **без жодної згоди**. Відсутність
   синхронізації нічого не ламає.

## Обсяг Фази 2

Розбитий на п'ять етапів. Порядок обов'язковий: кожен наступний спирається на
попередній, і після етапу C стенд уже можна тестувати наскрізно.

### Етап A — крипто-модуль web (без мережі)

- `apps/web/src/crypto/`: `encrypt(plaintext, aad)` / `decrypt(payload, aad)`
  на WebCrypto AES-256-GCM. Формат payload `0x01 ‖ nonce(12) ‖ ciphertext ‖
  tag(16)`; версійний байт збігається з версійним префіксом AAD.
- AAD рівно за §7: `"ndv1" ‖ 0x1F ‖ шлях ‖ 0x1F ‖ client_ts_ms ‖ 0x1F ‖
  ("0"|"1")`. `client_ts_ms` — десяткове ціле, мілісекунди UTC. Шлях
  валідується `^(entry:\d{4}-\d{2}-\d{2}|cycle|catalog|groups|settings|manifest)$`.
- Ієрархія ключів: `R` = 32 випадкові байти; HKDF-SHA256 → `k_enc`
  (`"ndv1:enc"`), `k_index` (`"ndv1:index"`), `k_auth` (`"ndv1:auth"`).
- `record_key = HMAC-SHA256(k_index, канонічний шлях)[:32]`; HMAC-таблиця
  `record_key → шлях` для всього діапазону дат + п'ять синглтонів.
- KDF: Argon2id (WASM) `m=65536 KiB, t=3, p=1`, сіль 16 байтів, вихід 32;
  fallback PBKDF2-HMAC-SHA256 через WebCrypto, ціль 1 000 000, підлога 600 000.
- **Клієнтська перевірка підлоги параметрів**, що прийшли з сервера: `argon2id`
  з `m_kib < 47104`, або `t < 1`, або сіль < 16 байтів → відхилити. Без цього
  скомпрометований сервер віддає параметри рівня «одна ітерація».
- `kdf_params` в AAD конверта біндяться **явним 0x1F-кодуванням**, не
  канонічним JSON: колонка `jsonb` не зберігає порядок ключів.
- Manifest рівно за §7, включно з дайджестом вмісту. Над **живими** записами
  (`deleted = false`); сам запис `manifest` не входить ані до переліку, ані до
  `n_live`.
- Політика фрази §7: основний шлях — згенерована фраза з 6 слів
  (72 біти); власна — ≥12 символів **і** ≥3 слова, або ≥16 символів для одного
  слова. Індикатор сили не показується. Hint не реалізується. Recovery-файл
  відхилено — не додавай його ні в якій формі.

### Етап B — серверні sync-ендпоінти

- `POST /v1/sync/push` із push-транзакцією §9.1 **у точному порядку семи
  кроків**, включно з `SELECT … FOR NO KEY UPDATE` на `account` як першим локом
  і per-key conflict-check **під локом**.
- `GET /v1/sync/pull` з курсором, `410` за горизонтом компакшну, `reset: bool`,
  `consent_state_changed: bool` (нейтральне, без назви kind).
- `GET/POST /v1/sync/key` із CAS по `wrap_version`; **step-up обов'язковий на
  будь-який запис**. `wrapped_dek_prev` з TTL 7 днів, перезаписується не
  частіше ніж раз на 24 год, віддається лише при step-up.
- `POST /v1/account/vault-reset` (step-up).
- Ліміти: payload per record 64 KiB → 413; per-account rate limits §11
  (sync 60/хв, push-обсяг 5 MiB/хв, **`GET /v1/sync/key` 10/год**) — вікна в
  PostgreSQL, без Redis.
- Компактор: DELETE tombstone-ів за `T_tomb`, в одній транзакції з
  `compacted_up_to = GREATEST(compacted_up_to, max(revision видалених))`.
- **Колонка `consent.record_key_cycle` і поле grant-контракту** — міграцією
  `0003`. У Фазі 1 її свідомо не заводили: клієнт уперше вміє обчислити
  `HMAC(k_index,'cycle')` саме зараз. Споживач (hard-DELETE при відкликанні,
  §9.7) лишається Фазі 3 — заведи колонку і приймання значення, але не DELETE.

### Етап C — web sync-модуль і UI (після нього стенд тестується наскрізно)

- `apps/web/src/sync/` — **єдине** місце серіалізації домену у vault-записи і
  назад. Reducer домену не змінюється. Тут же журнали видалень
  (cycle/catalog/groups) на межі серіалізації і клієнтська гігієна initData.
- Merge за §9.3: per-record LWW за автентифікованим `client_ts` зсередини
  payload; tiebreaker — per-device випадковий `device_id` усередині
  шифрованого payload; `DraftEntry` ніколи не перемагає `DoneEntry` тієї ж
  дати; tombstone ≥ update. Синглтони `cycle`/`catalog`/`groups` — поелементний
  merge (2P/OR-set) із журналами всередині payload, обрізаними за `T_journal`.
- Пост-410 правило авторитетності присутності §9.4, разом із **винятком для
  неактивних згод**: pruning не виконується без свіжої відповіді
  `GET /v1/consents`, не старшої за цей самий pull. Без винятку відкликання
  `cycle_sync` стирало б локальні `cycleStarts` — найтяжчий можливий дефект.
- Захист від масового видалення вкраденою сесією: >20% **і** ≥10 локальних
  записів у одному pull-батчі → підтвердження на пристрої.
- Initial upload чанками ≤200 records / ≤1 MiB, `base_revision=0`, послідовно;
  **manifest оновлюється в кожному чанку**, не один раз наприкінці.
- UI: діалог згоди (текст із `consent-copy/`, хеш надсилається в grant), екран
  парольної фрази з підтвердженням введення, перемикачі в Налаштуваннях за
  §5 Gate D, чесні стани помилок. Тексти беруться з реєстру, **не вигадуються**.
- CSP (§13.17): `script-src 'self'` несумісний з обов'язковим
  `telegram-web-app.js`, а Argon2id/WASM потребує `'wasm-unsafe-eval'`. Визнач
  точну політику й зафіксуй її в тесті; надто строгий CSP тихо зіштовхне всіх
  на PBKDF2.

### Етап D — компакшн, re-key, стійкість

- Re-key = vault-reset + повторний upload під новим DEK в одному клієнтському
  флоу; `key_version + 1`; ревокація інших сесій.
- Зміна фрази (re-wrap) — нова сіль, той самий `R`, `wrap_version + 1`;
  обов'язкова передумова: користувачка вводить **поточну** фразу.
- Бенчмарк KDF за наперед зафіксованим правилом §7: еталонні пристрої A
  (low-end Android, вимір у вбудованому WebView Telegram, **не** в окремому
  Chrome), B (iPhone SE 2020), C (desktop Chrome як контроль); поріг
  **p95 ≤ 3000 мс** на A з індикатором прогресу. Не проходить → щаблі `m`
  (64 → 47 МіБ), і лише вичерпавши їх — PBKDF2 з калібруванням у [600k; 1.2M].
- Демо-дані §9.6: sync-модуль вимкнений build-флагом у test/e2e-збірках, окрім
  спеціальної sync-e2e збірки; CI-перевірка, що prod-бандл не містить `genDemo`.

## Блокери, які ти не маєш права обійти

1. **Тексти згод лишаються `0.9`, контролер не названий.** Ім'я не вигадується,
   версія не позначається `1.0`. Fail-closed guard уже реалізований і має
   лишитися: у production-конфігурації згода з незамороженим текстом не
   створюється. Для тестового стенду використовується `APP_ENV=development` —
   і цей факт має бути видимим в UI стенду, а не замовчуваним.
2. **Словник на 4096 слів для генератора фрази не існує.** Він потребує
   локалізаційного редактора (виключити омоформи, слова, що плутаються на слух,
   і будь-яку медичну семантику). Це найбільший важіль на реальну стійкість у
   всій криптомоделі: без нього фраза захищена на ~30 бітів замість 72.

   **Рішення власника: готуй кандидатний словник.** Порядок:
   - збери українську лексику з відкритого джерела; зафіксуй джерело й ліцензію
     в `wordlist/README.md`;
   - застосуй механічні фільтри й закрий кожен тестом: рівно 4096 унікальних
     слів; довжина 4–9 літер; унікальний префікс перших 4 літер (щоб автодоповнення
     не вимагало вводити слово повністю); лише малі літери українського алфавіту;
     стоп-список медичної та неврологічної семантики (`невро`, `симптом`,
     `мігрен`, `епілепс`, `склероз`, `здоров`, `діагн`, `біль`, `напад`, `лік`
     та латинські відповідники); без слів, що збігаються за звучанням у списку
     омофонів, який ти складеш явно;
   - позначи файл у коді **як такий, що НЕ пройшов локалізаційний review**, і
     заведи це окремим рядком у `docs/plans/backend-bot-plan-progress.md`;
   - **UI не оголошує «72 біти» і не показує індикатор сили**, доки словник не
     погоджений редактором. До того — нейтральне формулювання про те, що фразу
     згенеровано застосунком.

   **Заборонено:** брати слова «з голови» замість джерела, і оголошувати
   стійкість, якої словник ще не має.
3. **Бенчмарк KDF — вимір, а не переговори.** Правило прийняття зафіксоване
   наперед у §7. Якщо вимір недоступний (немає еталонного пристрою), зафіксуй
   це у звіті й лиши PBKDF2 за замовчуванням — не «оціни на око».

## Дисципліна якості

- **TDD**: спершу тест, який падає. Для крипто — тести на властивості
  (повторне шифрування → різні nonce і ciphertext; payload під чужим
  `record_key` → відхилення). Для конкурентності — інтеграційні на реальній
  PostgreSQL через testcontainers.
- **Локальний Docker.** На цій машині testcontainers падає з
  `mkdir /host_mnt/.../docker.sock: operation not supported`. Робочий обхід:
  `TESTCONTAINERS_RYUK_DISABLED=true uv run --locked pytest`. У CI не потрібен.
- **Міграції `0003`+, а не правка `0001`/`0002`.** Обидві застосовані й
  змерджані. Нова міграція мусить мати робочий `downgrade`.
- **Наскрізні gates перед закриттям фази** (усі мають бути зеленими):

```bash
pnpm test && pnpm build && pnpm e2e
```

```bash
cd apps/api && TESTCONTAINERS_RYUK_DISABLED=true uv run --locked pytest && uv run --locked ruff check . && uv run --locked ruff format --check . && uv run --locked mypy --strict app && uv run --locked lint-imports
```

```bash
cd apps/bot && uv run --locked pytest && uv run --locked ruff check . && uv run --locked mypy --strict bot
```

```bash
cd apps/api && uv run --locked pytest tests/unit/test_initdata_validator.py --cov=app.infra.telegram.initdata --cov-branch --cov-fail-under=100
```

- Роутери тонкі; бізнес-логіка в `app/services/*`; ORM і сесії не вище
  `infra/db/repositories`; жодного SQL у роутерах.
- `main` під strict branch protection: працюй у гілці, відкривай PR. Комміти з
  префіксом `phase-2:`. Секрети не комітити ніколи.

## DoD Фази 2 (acceptance-критерії)

Повний перелік — `backend-bot-plan.md` §12, Фаза 2, разом із блоком «Додано
після Gate D». Наприкінці фази онови
`docs/plans/backend-bot-plan-progress.md`: заміни `_pending_` на конкретний
доказ (назва тесту, номер CI-прогону), як це зроблено для Фази 1.

Мінімум, що має бути під тестом:

- два конкурентні push одного `record_key` з однаковим `base_revision` →
  рівно один 200 і один 409, на реальній PostgreSQL;
- property-тест: tombstone не перезаписується мовчки;
- property-тест: монотонність ревізій;
- застарілий pull після компакшну → 410; застарілий push → 410;
- після повного ресинку видалений ключ не воскресає;
- клієнт відхиляє payload під чужим `record_key`;
- повторне шифрування дає різні nonce і ciphertext;
- спільні JSON-фікстури web↔api, включно з новим валідатором
  `sym ∩ absent = ∅` у `DoneEntry` (§13.13 — його свідомо лишили Фазі 2);
- cycle merge для delete / offline-add / re-add збігається за ≤2 раунди;
- Playwright синхронізує два браузерні профілі через локальний api;
- дамп БД не містить plaintext контрольних нотаток, **і** `vault_record` не
  містить рядка, що парситься як ISO-дата або як ім'я синглтона (це перевіряє
  саме усунення plaintext-заголовка);
- manifest — **обидві** гілки: «вилучено живий запис → перевірка падає» і
  «вилучено compacted tombstone → перевірка проходить»;
- два конкурентні re-wrap → рівно один 200 і один 409 по `wrap_version`;
- запис у `/v1/sync/key` без step-up → 403;
- e2e: `location.hash` і `sessionStorage` очищені від initData.

## Відхилення від плану

Якщо пункт плану виявиться технічно хибним — не обходь мовчки: зупинись,
зафіксуй проблему, запропонуй мінімальну правку й онови
`docs/plans/backend-bot-plan.md` окремим комітом. Privacy-правила вище,
блокер з іменем контролера і блокер зі словником — не предмет відхилень.

Окремо: §7 і §9 уже пройшли адверсарну перевірку (30 підтверджених знахідок
інтегровано) і наскрізне узгодження Gate D. Якщо тобі здається, що якесь
рішення помилкове, спершу перечитай §13 — ймовірно, твоє заперечення вже
розглянуте там серед залишкових ризиків.

## Звітність

Наприкінці — звіт у чаті: що зроблено; DoD-чекліст «пункт → тест/артефакт»;
дослівні результати всіх gate-команд (pass/fail, без переказу); результат
бенчмарку KDF або явна фіксація, що вимір недоступний; відхилення від плану;
що лишилося за людиною. **Перед закриттям фази проведи незалежний code-review
субагентом**, передавши йому privacy-правила цього промпту — у Фазі 1 такий
review знайшов дев'ять дефектів, серед них обхід anti-replay, який пройшов усі
власні тести автора.
